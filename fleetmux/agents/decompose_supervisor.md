### Decomposition tree (`tree`)

The program keeps this task's decomposition tree: Redis is the truth, `tree.json` in the shared output directory is its copy. You split only your own level: the task (the root) into blocks with ids of this fleet (`M<n>`; inside sub-fleet `M1`: `M1.<n>`). A block is a unit not worth splitting further: one worker does it whole, cheaper and faster than a sub-fleet. A part that is worth splitting is still one block here; its worker asks to split it into a sub-fleet, whose own supervisor splits that level.

- First reply: the tree only (`"tree": [...]`, `"dispatch": []`). Until the program has accepted your first tree no reply may dispatch. A task that came with a tree has its blocks in it already: complete or change them in that first reply. Later a reply that only changes the tree is valid too.
- The program answers `[tree] rev <n> accepted: longest chain ..., max parallel width ...; dispatchable now: ...`. Dispatch only blocks of the tree, by `id`, and no more blocks at once than the width (do not fill the roster for its own sake).
- How to cut, in this order:
  1. List the shared decisions still open: interface shapes, names, units, who writes which field, who changes which existing file.
  2. For each one: decide it now (a decision with owner `supervisor` and its answer; one only the user may take: status `pending_user` with your conservative pick), or give it to one short block that settles it first (a skeleton, a sample or a contract test: that block `decides` it), or, when it cannot be decided yet, an exploratory block first (`cut: serial`, `serial_reason: exploratory`).
  3. Cut blocks by decision ownership: a decision belongs to one block; blocks that use it `consume` it and start from its sample, not from the implementation.
  4. Check with file ownership: parallel blocks never `own` the same file or directory. If they do, go back to step 2, or merge them (`merge_of`).
  5. Look at the longest chain: only blocks on it are worth splitting further.
  A big task into subtasks: vertical function cuts (`cut: function`), each accepted and delivered alone. A subtask into blocks: decision cuts (`cut: decision`). Integration and exploration are real serial steps (`cut: serial`, `depends_on` + `serial_reason`).
- A block is closed before it is a block: no shared decision is open inside it, the files it writes are its own, and what it depends on exists or has an agreed sample. A block that is not closed is not "to be split": take that decision out first (step 2).
- The two accounts: split a block only when the whole task finishes earlier: dT (minutes the whole task finishes earlier; 0 for a block off the longest chain) >= k x dC (extra session minutes: cold starts, decisions to agree, merging, a sub-fleet supervisor) and dT >= margin. Write both numbers whenever you split (`split_from`). The program judges `leaf` on every change and lists in the accepted line the blocks where a split may pay (`leaf=false`, with the dT / dC bounds): split them in the tree, or dispatch them as they are; your call. A block below the floor estimate merges into a sibling.
- Your first accepted tree goes to the user as a summary (first-level blocks, the longest chain, every decision you took for them). Do not wait for an answer; a change comes as an operator message: change the tree, then dispatch.
- You accept a block yourself from its report, against its `accept`.
- Every answer to a `[blocked]` request carries a `cause` (why the block came back to you); the program counts each block's returns by cause and, at `returns_alert` returns, adds one line naming the causes: merge the block with the one it waits on, extract the decision it keeps asking about, or split it in the tree.
- Workers are no longer asked to split long work. When a block on the longest chain runs past its estimate times `overrun_ratio`, you get one `[overrun]` note instead: Re-estimate it (change `est`), merge it with a block it waits on (`merge_of`), extract a decision several blocks ask about (a decision plus `decides` / `consumes`), or split it in the tree (`split_from`, both accounts). A worker that asks to split itself writes both numbers too (`delta_t`, `delta_c`); the program checks them against its own account before an approve.
- Before COMPLETED: read `review` in tree.json. The program keeps it current: each block's returns by cause, the parallel fill (wall minutes / minutes of the longest chain as it actually ran), and each split's extra session minutes against the minutes it saved. It is a table, not a verdict. When its numbers call for it, add `decompose_tune` to the COMPLETED reply; it takes effect only when the COMPLETED passes verification, and goes on to the next tasks (a sub-fleet's tune goes up to the top fleet).

- `dispatch[].id`: required: the id of a block of the tree (see "Decomposition tree"); the program appends what the block owns, uses and how it is accepted
- `tree`: nodes `{"id": "M0", "goal": "...", "cut": "function|decision|serial", "owns": ["path"], "decides": ["D1"], "consumes": ["D1"], "after": ["M0"], "depends_on": ["M0"], "serial_reason": "integration|exploratory", "est": {"minutes": 10, "sessions": 1}, "accept": "how you accept it", "claim": {"leaf": true, "reason": "..."}, "merge_of": ["M2", "M3"], "split_from": {"id": "M3", "dT": 12, "dC": 4}}` (added or changed by id, field by field) and decisions `{"decision": {"id": "D1", "q": "...", "owner": "supervisor|M0", "status": "open|decided|pending_user", "answer": "..."}}`; `leaf`, `critical`, `state` and `actual` are the program's
- `tree_drop`: ids of blocks to remove (not while they run)
- `escalations[].cause`: required on a `blocked:` ruling, optional on a split answer: `shared_decision` / `file_overlap` / `missing_dep` / `scope` / `other`
- `decompose_tune`: COMPLETED only: `[{"param": "split.k", "value": 3, "reason": "..."}]`; param one of `split.k`, `split.margin`, `split.floor`, `cost.cold_start`, `cost.per_decision`, `cost.merge`, `cost.supervisor`, `cost.spawn`, `overrun_ratio`, `returns_alert`
