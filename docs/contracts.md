# fleetmux external contracts

fleetmux is general-purpose infrastructure and knows nothing about any business domain (trading, research reports, …). Business projects (consumers) use it only through the interfaces listed on this page.
Any change to an item below must be announced to, and synced with, the consumers in the same batch; you may add but not change, and a change of semantics needs a transition period.

This page is extracted from the code (section 8 records the channel interface freeze). Where the code and this page disagree, the code wins and this page gets fixed.

## 1. kit directory (built on the project side, read-only to fleetmux)

Defined in: the header of `fleetmux/kit.py`.

```
DIR/core/CLAUDE.md                 core project rules (no domain index, no memory)
DIR/context_domains.yaml           domain table: summary / triggers / rules / skills / agents / mcp
DIR/domains/<domain>/RULES.md      domain rules (the table's rules field, relative to DIR)
DIR/domains/<domain>/skills/<name>/
DIR/domains/<domain>/agents/<name>.md
DIR/mcp.json                       full MCP set, started with every Claude worker
DIR/fleets/<name>/roster.yaml      roster template for start --kit-fleet (fleet.py copies it into the run; kit.py does not read it)
```

A kit carries no memory. Domain names match `[a-z0-9][a-z0-9_-]{0,63}`, entry names `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`; an invalid kit is rejected as a whole.
The kit is generated by the consumer's own build script.

## 2. Roster

Defined in: `fleetmux/roster.py`, `docs/design.md` §29.

- Slot names under `workers:` always end in `-<number>` (new runs reject non-conforming names); rotation keeps `<name>.<generation>`.
- The advisor is not a worker: it is configured only by the top-level `advisor: on|off` and never appears under `workers:`.
- Long-task splitting uses the top-level `split:` and a worker entry's own `split:` (`check_minutes`, `window_minutes`, `min_calls`, `min_distinct`, `restore_model`; defaults 40 / 10 / 15 / 2 / true; `check_minutes: 0` = no reminder); a bad value rejects the whole roster; `docs/design.md` §44.
- Extra tabs use the top-level `tabs:` (`docs/design.md` §31): each entry is `{name, command, cwd?, env?}`; optional `restart: on-exit` (the only accepted value; omitted = the tab is opened only once when the daemon starts), `backoff: {first_s, max_s}` (default 5 / 300 seconds), `crashloop: {restarts, minutes}` (default 5 restarts / 10 minutes); the latter two may only be written together with `restart: on-exit`, and bad values reject the whole roster. After the program exits it is reopened following the backoff; once `restarts` reopens have happened within `minutes` minutes and it exits again, it stops (audit `tab.crashloop`, a notice card in the supervisor column, and `tab_crashloop` pushed when a channel exists), and `fleetmux tab restart <name>` recovers it. Audit events: `tab.cleared` / `tab.started` (on reopen with `reason` = exited / operator and `attempt`) / `tab.start_failed` / `tab.dock_failed` / `tab.stopped` / `tab.down` / `tab.crashloop` / `tab.restart_requested` / `tab.check_failed` / `tab.notice_failed`. Display name: when the run comes from a kit (config `kit_fleet`, inherited by named sub-fleets) the tab title is `kit-<n>-<name>` (n counts from 1 in `tabs:` order), otherwise `name`; the `tab` in the registered identity and in the audit is still the name.
- Named sub-fleets are declared with `subfleets:` (`supervisor_slot`, `autostart`, `roster`, plus the overrides `claude`, `worker_model`, `stall_timeout`, `max_busy`, …; the full list is `NAMED_OVERRIDES` in `subfleet.py`) and can be hot-reloaded.

## 3. Sub-fleet keys in the parent Redis

Defined in: the header of `fleetmux/named_subfleet.py`. External consumers: the consumer's bridge program (reads `redis_socket`) and the consumer's engine (sends `subfleet.up` / `subfleet.down`).

```
fx:subfleet:<name>      hash: state (down / starting / up / paused / draining), slot, redis_socket,
                        run_dir, up_at, drain_since, drain_reason, crashloop, usage_at
fx:subfleet:opq         list: ids of external operations still open
fx:subfleet:op:<id>     hash: op, name, reason, status (awaiting / approved), created, approved_at
```

External operations arrive as service requests: `{"id", "op": "subfleet.up" | "subfleet.down", "name", "reason"}`; the result is published as usual on `fx:result:<id>`.

## 4. Command line

Command name `fleetmux` (design.md §50): the Rust binary execs every subcommand it does not handle itself (all of those in the table below) unchanged into the Python command line of the same release, with identical arguments, output and exit codes. Without the Rust binary, the same command line is `<release>/.venv/bin/fleetmux-py <subcommand>` or `python -m fleetmux.fleet <subcommand>`. Make sure the `fleetmux` on a machine's `PATH` is a post-§50 version (an old one reports usage and exits 2).

Consumers call the `fleetmux` command (Python package `fleetmux`).

| Consumer (typical use) | Subcommands used |
|---|---|
| Daemon of a resident service fleet | `start` (`--lifecycle --resume --worker-cli --worker-model --worker-names --supervisor-cli --supervisor-profile --max-busy --redis-runtime-dir --redis-server`, etc.) |
| Bridge program reading sub-fleet state | `status`, plus the keys in section 3 |
| Request/response service caller | `start` / `stop` / `status` / `request` |
| Scheduled-report driver | `start` (`--lifecycle --advisor --worker-kit --worker-domains --stall-timeout`, etc.) / `task` / `status` |

`start --request-timeout` (design.md §43): **unset** by default (the old default was 900 seconds). A service request without `timeout_s` no longer expires by wall clock; when one does time out (it carries `timeout_s`, or `--request-timeout` was given explicitly), only the worker slot running it is held and `timeout` is published — the whole fleet is no longer paused. The `fx:result:<id>` status set and "a late answer is not used" are unchanged (a late answer is audited separately as `result.late`). Existing consumers are unaffected: consumers that send their own `timeout_s` with every request (for example 120 or 900) keep it, a consumer that only sends `subfleet.up` / `subfleet.down` is never subject to `request_timeout`, and consumers that do not pass `--request-timeout` see no change. Runs already running keep the old default 900 stored in their config.json and `start --resume` keeps it; only a fresh `start` becomes unset.

`start --lease-reclaim on|off` (design.md §24 "lease reclaim"): default `on`, written to `lease_reclaim` in the run's `config.json` (only `on` / `off` are accepted; any other value is rejected by config validation in `start` / `--resume` / daemon startup). `start --resume` changes it if given and keeps it otherwise; an old run without the key (or with value `null`) counts as `on`. `on`: when an official Claude / Codex slot's lease expired only because the daemon was not running (lid closed / sleep, daemon stuck) while the dispatch deadline has not passed, the daemon reclaims the lease and the turn settles normally — the slot is not held, nothing is paused, and the service request is not judged `timeout`. `off` = the old behavior (a task worker holds only that slot; service / supervisor hold and pause). The consumers above need not change their arguments. Also, when a task-mode worker slot is released from hold, the supervisor receives a `[<slot> report]\nHELD-RELEASED: …` (with the tail of the turn's last text, ≤ 4000 characters), and the `hold.released` audit carries `notified`; new audit events `lease.reclaimed` (`gap_s`) and `daemon.gap` (`gap_s`, `slots`); the bus audit stream gains a `reclaimed` kind.
`operator` (design.md §48, available to external callers): `fleetmux operator --config <run>/config.json "<text>"` (no text or `-` reads stdin; `--wait` seconds, default 30). Sends the operator text to the current supervisor over the fleet's private Redis (an `operator_input` event, same semantics as typing by hand in the supervisor pane: service creates a `ui-` request; task adds it as an `[Operator instruction]` supplement when there is a task and creates a task when there is none), **without touching any pane's input box**. stdout is one JSON line: `{"status":"accepted","id"|"task_id":…}` with exit code 0; `{"status":"rejected","reason":…}` with exit code 2 (Codex supervisor, old Claude supervisor without a hook mailbox, old generation, not ready, v1 run — each has an explicit reason); `{"status":"pending","request_id":…}` with exit code 3 (in the stream but unconfirmed — do not resend; check control / `logs` first). Replaces typing into the supervisor pane with `cmux send`.
`tab restart <name> [--config <run>/config.json] [--wait <seconds>]` (design.md §31, available to external callers): makes the running daemon immediately reopen this tab from the roster's `tabs:` and clears its crash counter (the recovery entry after the breaker trips). One JSON line on stdout: `{"status":"accepted","tab","title","pane"}` exit 0; `rejected` (the roster has no such tab / this daemon never opened it / the request expired) or `failed` (cannot be opened) exit 2; `pending` (the daemon did not handle it within `--wait`, default 30 seconds) exit 3. It goes through the fleet-private Redis: `fx:tab:restart` (hash, tab name → `{"id","at"}`) and `fx:tab:reply:<id>` (the reply, EX 3600).
`start --no-claude-hook-delivery` / `--clear-after-result` (§48): the flags remain but are rejected at startup (both would require typing into Claude's input box); `claude_hook_delivery: false` / `clear_after_result: true` under the roster's `subfleets[]` rejects the whole roster. None of the consumers above pass them.

## 6. pi project hook (P1, merged with the pi / dsh line)

The pi extension `extensions/project-domains.ts` calls a domain script provided by the consumer:

- stdin is one JSON: `{"session_id", "session_file", "prompt"}` (before a session starts) or `{"session_id", "session_file", "path"}` (after a file is read or written).
- stdout is one JSON: `{"domains": [newly loaded domains], "text": "content to hand to the model"}`; no match or already loaded → `domains` is empty.
- Any exception in the script lets the call through: it outputs an empty result.

## 7. Cross-session progress board (M0)

Claude Code / pi sessions that know nothing about each other each keep one record on the progress board; when two of them change the same place, each side receives one "collision notice". The rule is first come, first served: the first session continues, the later one stops touching the conflicting files and waits until the first one finishes and the fleet supervisor releases it (the supervisor that every fleetmux start brings up coordinates all collisions). This module stops neither side and merges nothing; "waiting" relies on the notice text and the supervisor's release message. Code: `fleetmux/session_board.py` (standard library only).

- **Location**: `~/.fleetmux/board/`, overridden by `FLEETMUX_BOARD_DIR` (tests always use a temporary directory). One `<agent>-<session_id>.json` per session, written to a temporary file and then renamed; `errors.log` in the same directory collects every exception (rotated to `.1` past 1 MB).
- **Record**: `session_id`, `agent` (claude / pi), `name`, `cwd`, `pid` (pi only), `page` (written only when `FLEETMUX_PAGE` is set), `goal` (the user's most recent message verbatim, cut to 160 characters; a prompt wholly wrapped in one pair of tags — background notices like `<task-notification>…</task-notification>` — or blank does not count, and the previous one is kept), `updated_at`, `ended_at`;
  - `touches`: `{repo, worktree, branch, path, ts}`, recorded by the repository of the **changed file** (not the session's cwd); `repo` = the real path of `git rev-parse --git-common-dir`, so several worktrees of one repository count as one repository; `path` is relative to the worktree;
  - `git_events`: `{repo, worktree, branch, op, target, ts}`, `op` ∈ commit / merge / checkout / worktree_add, best-effort parsed from Bash commands including `git -C <dir>` and `cd <dir> &&`; a merge's `target` is the branch checked out at the time;
  - `notified`: notices this session has already received; key = the other side's `agent:session_id|repo`, value = the rules and files already reported;
  - `since`: `{repo: ts}`, when this session first changed a file in that repository; changing the same file again leaves it alone; changing again after the last change in that repository is older than the TTL resets it (counts as a fresh start);
  - `collisions`: collision pairs this session has seen, keyed like `notified`, value `{repo, other, first, files, targets, at, ts}`; `first` is the first comer `agent:session_id` fixed when the collision was first found (a pair that has not collided again within the TTL counts as a new occurrence and is re-decided); at most 100 kept;
  - `inbox`: messages others left for this session with `note`, `{from, text, ts, delivered_at}`; at most 50 kept; after delivery only `delivered_at` is set and nothing is deleted (`list` relies on it to judge "released").
- **Online**: no `ended_at` written (written by Claude `SessionEnd` / pi `session_shutdown`), `updated_at` within the TTL (default 2 hours, `FLEETMUX_BOARD_TTL_S`), and the recorded `pid`'s process (if any) still alive.
- **Collision**: two online records share a repo and either holds: ③ both changed the same repository-relative path (across worktrees too); ④ both merged into the same branch within the merge window (default 30 minutes, `FLEETMUX_BOARD_MERGE_WINDOW_S`). Same worktree or same branch alone (the former ① ②) no longer counts as a collision — a dozen sessions are routinely open on the same main worktree at once, and judging by ① ② would deadlock them; they only appear as background in the notice text. The same other side in the same repository is reported once; a new rule or a new shared file triggers another report.
- **Order**: decided per repository, not per file. The first comer = the side with the earlier `since` in that repository (for an old record without `since`, the smallest `touches[].ts` within the TTL; for a side that collided only by ④ and changed no file in that repository, its earliest `git_events` time in that repository within the TTL); on a tie, the smaller `session_id` in lexical order comes first.
- **Notice text**: the later comer receives 「⚠ 撞车：<对方> 先开始动 <仓库> 的 <文件>（<n> 分钟前），按先到先得由它继续。你先别再改这些文件，可以做别的；等它完成，由监工协调后再继续。背景：…。对方目标：…。」 ("⚠ Collision: <other> started on <file> in <repo> first (<n> minutes ago); first come, first served, so it continues. Stop changing these files for now, you may do other work; once it finishes, continue after the supervisor coordinates. Background: …. Other side's goal: ….") with `n` counted from the other side's `since`; the first comer receives 「⚠ 撞车：<对方> 也碰了 <仓库> 的 <文件>。你先开始，由你继续；对方会等你完成。完成后监工会协调对方接着做。背景：…。对方目标：…。」 ("⚠ Collision: <other> also touched <file> in <repo>. You started first, so you continue; the other side will wait for you to finish. After you finish, the supervisor will coordinate the other side to carry on. Background: …. Other side's goal: …."). When the collision is by ④ only, the file is replaced by the merge target (「先开始往 <仓库> 的 main 合并」 "started merging into main of <repo> first", 「你先别往 main 合并」 "do not merge into main for now"). The background names the other side's worktree and branch in that repository, and says 「同工作树」 ("same worktree") when it is this session's worktree.
- **`list [--json]`** (read-only; creates no directory and writes no file): `python3 <fleetmux>/fleetmux/session_board.py list`. Three parts: online sessions (name, agent, `agent:session_id`, goal, last update); collision pairs (repository, files / merge target, first comer, later comer, whether the first comer has finished, who has released it); awaiting coordination (pairs whose first comer has finished and whose later comer has not been released yet). Collision pairs come from `collisions` in the online session records, with the two sides' views merged into one pair; pairs whose later comer has gone offline are not listed. The first comer has "finished" = it wrote `ended_at`, its process is gone, or all its changes / git actions in that repository are older than the TTL; the finish time is `ended_at`, `updated_at`, or the last change + TTL respectively. "Released" = the later comer's `inbox` has a message after the finish time; pairs released longer than the TTL ago are no longer listed; nor are pairs whose later comer had not itself received this collision notice yet when the first comer finished (it was not waiting). `--json` outputs `{sessions, collisions, pending}`, each pair `{repo, repo_name, files, targets, first, later, first_done, released: [{from, ts, text}], pending}`.
- **`note <other> <text> [--from <sender>]`**: the other side is given as `session_id`, `agent:session_id`, or a name; for a duplicate name only online sessions are considered, and if more than one remains it errors out listing the candidates rather than guessing. Writes into the other record's `inbox` (taking that record's lock, waiting at most 5 seconds); the sender defaults to `supervisor`. On the other side's next Claude hook (taken only on events whose output reaches the model, such as SessionStart / UserPromptSubmit / PostToolUse) or the pi extension's next board write / 30-second comparison, it is delivered once as 「【进度板留言】来自 <发送者>（<n> 分钟前）：<文字>」 ("[Progress board message] from <sender> (<n> minutes ago): <text>"), ahead of any collision notice; unmanaged pi sessions follow the delivery rules above (busy: steer; idle: steer + triggerTurn). Errors from `list` / `note` go to stderr with exit code 1, never swallowed.
- **Supervisor duties**: the five supervisor prompts (`supervisor.md` / `supervisor_v2.md` / `service_supervisor.md` / `service_supervisor_v2.md` / `service_supervisor_tui_v2.md`) each have the same section "Cross-session collisions (the session board)", and the fleet replaces `{{SESSION_BOARD}}` with `<python> <fleetmux>/fleetmux/session_board.py`. After handling each business message, the supervisor runs `list` once, looking only at items awaiting coordination and new collisions; for each item awaiting coordination it sends the later comer one `note` releasing it, with coordination instructions where needed (rebase first / pull the latest main first); it only decides who continues, who waits and when to release, and never changes any session's task goal; if `list` shows a pair already released (including by another fleet's supervisor) it does not send again; if the user has personally given instructions about a collision, the user's instructions win. The ban line "do not call the fleet command line" has an exception for these two commands. `contracts_supervisor.md` does not get the section: it is only appended, in contract tasks, after the base supervisor prompt that already carries the section, and `contract_doc()` only substitutes `{{WORKSPACE}}`, so adding it would duplicate the section and leak the raw placeholder.
- **Supervisor write access**: the Claude supervisor (`--dangerously-skip-permissions`) and the pi supervisor (not sandboxed, `HOME` unchanged) can read and write `~/.fleetmux/board/` directly. The Codex supervisor runs under `--sandbox workspace-write`; `actor_argv` lists the board directory (`session_board.board_dir()`, follows `FLEETMUX_BOARD_DIR`) together with the roster directory in `sandbox_workspace_write.writable_roots`; a run without a roster still gets the board directory; workers never get it. Verified with a real `codex exec` on codex-cli 0.164: without the board directory `note` fails with Operation not permitted; with it, the message lands in the other side's inbox.
- **Claude Code entry point**: `python3 <fleetmux>/fleetmux/session_board.py hook claude`, hooked on SessionStart / UserPromptSubmit / PostToolUse (matcher `Edit|Write|MultiEdit|NotebookEdit|Bash`) / SessionEnd. stdin is the hook JSON; when there is a new notice, stdout is one JSON: `{"systemMessage": text, "hookSpecificOutput": {"hookEventName": event name, "additionalContext": text}}`; SessionEnd never outputs anything. Edit / Write / MultiEdit / NotebookEdit record `file_path` / `notebook_path`, Bash records the command, other tools record nothing. Delivery happens only when this session acts (a `note` message also waits for this session's next action; an idle Claude session waits for the user's next message).
- **pi entry point**: the extension `extensions/session-board.ts` (installed into `~/.pi/agent/extensions/` by `launchers/install-session-board.sh`, with the Python placed beside it as a symlink) calls the same Python via `pi.exec("python3", [script, "hook", "pi", JSON])`; stdout is the notice text. session_start / input / tool_result (edit, write, bash) / session_shutdown write to the board, plus a comparison every 30 seconds (the timer is cleared on session_shutdown). Delivery: busy → `deliverAs: "steer"`; idle → `steer` + `triggerTurn` to wake it; right after user input → `nextTurn`. Fleet-managed panes (environment has `FLEETMUX_PI_SLOT` / `FLEETMUX_PI_BRIDGE` / `FLEETMUX_PI_CALLBACK`, see `pi_adapter.py` `environment()`) use only `nextTurn` — this is a defensive branch: managed panes now start with `--no-extensions` and an isolated `PI_CODING_AGENT_DIR` (`pi_adapter.py` `argv()` / `environment()`), so they cannot load this extension, and supervisors / workers are currently not on the board. `PI_SESSION_BOARD=0` turns it off.
- **Errors never get in the way**: any exception in either entry point is swallowed, with exit code 0 and no output; it is only written to `errors.log`. git query results are cached only within a single process; a single hook measured about 35–65 ms.

## 8. Channels (WeChat / Feishu / Telegram / email / exec push; interface frozen at P0)

Defined in: `fleetmux/channels/__init__.py` (registry, roster rules, paths, key names, audit names), `channels/base.py` (adapter base class), `channels/envelope.py` (envelope / origin / outbound item / card / command / receipt); design in `docs/design.md` §53. Contract tests: `tests/test_channels_contract.py`. After the freeze, changing any item here = report to the supervisor → the core maintainer makes the change, this section is updated in step, and the commit subject starts with `contract:`; affected packages re-test.

**Roster `channels:` (new top-level roster key; `roster.py` calls `channels.parse_channels`)**

```yaml
channels:
  - {type: telegram, account: fleet-bot-1, push: [result, task_done, prompt_wait, run_closed]}
  - {type: email, account: fleet-mail, push: [task_done]}
```

- Each entry allows only the three keys `type` / `account` / `push`; `type` ∈ `telegram / feishu / weixin / email / exec / slack` (tests may add fake types with `channels.register`); `account` matches `[a-z0-9][a-z0-9._-]{0,63}`; a given `type:account` may appear only once (one credential, one consumer); **at most one `type: feishu`** (lark-oapi 1.5.3 allows only one WS client per process, and a fleet has only one actor process; P0b); at most 8 entries; `push` defaults to `result, task_done, prompt_wait, run_closed, daemon_down`, and the full set of selectable events is `result / task_done / prompt_wait / escalation / run_closed / daemon_down / security` (`escalation` is off by default; `security` is P8a's security alert push, on by default). The event `tab_crashloop` is also available (design.md §31: a tab with `restart: on-exit` tripped the breaker and stops reopening; on by default, i.e. both the default `push` value and the full optional set include it; the daemon LPUSHes `fx:channel:outq` directly with `target: last`, and only on the main service fleet that runs the channel actor). One bad entry rejects the whole roster; each error is written as `channels[i]: …`, and error text never echoes values. Credentials and allowlists **never** go into the roster.
- Order matters: when nobody has talked to the fleet yet, proactive pushes go to the first channel whose account file sets `PUSH_TO` (`PUSH_TO` is the explicit initial target). `PUSH_TO` is usable only when `Channel.private_target_ok(PUSH_TO)` is true — it must be the allowlisted user's own one-to-one conversation (Telegram / WeChat / email: the conversation id is the user id and must be in `ALLOW`; Feishu: a p2p chat id that an allowlisted open_id has messaged privately before, recorded in the store); otherwise it is treated as no target (`channel.no_target`), never bypassing the private-chat / allowlist rule. `PUSH_TO` **cannot make the bot open a conversation**: if the Telegram user has never messaged the bot (`/start`), the platform rejects the send (403); that push fails and is audited, and on-device acceptance must have the user `/start` first.
- Effective only in the roster of the main fleet in service mode with transport v2; a task fleet / sub-fleet roster with `channels:` → `start` refuses and explains (the first phase only talks to the resident service fleet on this machine). Hot reload: a change to `channels:` takes effect when the daemon restarts the channel actor. A fleet without `channels:` behaves exactly as before.
- **Where it lands in the run**: `start` (and hot reload) writes the entries from `parse_channels` unchanged into the top-level `channels` key of the run's `config.json` (a list; absent if not configured). All daemon-side readers — `lifecycle_close.notify`, `daemon_down_section`, P6's delete card, the actor — read only `cfg['channels']` and no longer parse the roster themselves.

**Origin lifecycle**: the actor writes the origin after receiving the `accepted` answer, `EX` 7 days (`ORIGIN_TTL`). In theory there is a window between the actor writing the origin and the worker finishing its answer, so when the outbound watcher sees **a result without an origin**: if the result's `at` is less than `channels.ORIGIN_GRACE_S` (60 seconds) ago → do not mark it pushed, check again next round; still none after 60 seconds → treat it as an external request (command line, another program, …), mark it pushed and do not send. A follow-up result `<id>.done` is mapped back to `<id>` with `envelope.origin_id` to find the origin (see "Handing large jobs to a task sub-fleet").

**Adapter interface (`channels/base.py`)**

- The module `fleetmux/channels/<type>.py` defines `ADAPTER = <base.Channel subclass>`, with `type` matching the registry; an import failure (e.g. Feishu without `lark-oapi`) only makes that channel `unavailable` (`channel.unavailable`) and does not affect other channels or the fleet.
- Construction: `Channel(account, *, transport=None, store=None, audit=None, inbox_dir=None, clock=time.time)`. `account` = `channels.Account` (`type, name, allow, values`); `transport` = the adapter's single network entry point (a callable whose signature the adapter documents in its module header; HTTP adapters use `base.http_transport`'s `(method, url, *, headers, body, timeout) -> (status, body)`, exec uses a subprocess entry point), `None` = the real default; tests always inject a fake one, never touching the real network or opening listeners.
- Class attributes: `TEXT_LIMIT` (maximum length of one message, Telegram 4000), `RECEIVES` (False for exec), `SUPPORTS_CARDS / SUPPORTS_BUTTONS / SUPPORTS_UPDATE / SUPPORTS_FILES`, `MAX_FILE_BYTES` (default 20 MB; anything larger goes to `rejected_files`, never silently dropped).
- Adapters implement only the underscored hooks (the one registered exception: Slack overrides the public `send_text` only to reset thread state before calling `super()`, see "Slack specifics"): `_send_text(conversation, text, reply_ref)` (one segment, ≤ `TEXT_LIMIT`), `_send_card`, `_update_card(conversation, message_id, card)`, `_send_file(conversation, path, caption, reply_ref)`, `parse_inbound(raw) -> [envelopes]`, `_poll(timeout) -> [raw]`, optional `start()` / `close()` / `check()`. They return the platform message id or a `SendResult`.
- Public methods are implemented by the base class and **never raise**: `send_text(conversation, text, *, reply_ref=None)` (splits by `TEXT_LIMIT`, preferring a newline in the second half of the window; the pieces joined equal the original), `send_card(conversation, card, *, reply_ref=None)` (no card / no button support → `card_text` writes each button's command as text), `update_card(conversation, message_id, card)` (unsupported → send a new card), `send_file(conversation, path, caption='', *, reply_ref=None)` (unsupported → send the path as text); any exception → `SendResult(ok=False, error)` + audit `channel.error`. `inbound(raw)` / `poll(timeout)`: parse → validate envelope → **uniform policy** (`sender ∈ ALLOW` and `private` and `verified`, otherwise `channel.drop_policy`, recording only who and which conversation, never the body) → seen idempotency (redelivery → `channel.drop_dup`); any exception is swallowed and audited, returning `[]`.
- `reply_ref` is interpreted only by the adapter (Feishu message_id for threaded replies, WeChat `context_token`, email `Message-ID` / `In-Reply-To`, Telegram `chat_id` / `message_id`); upper layers store and pass it unchanged.
- **Construction and injection**: keep the signature above; no separate `Adapter(account, creds, *, http, clock, state)`: credentials are read by the upper layer and placed into `Account.values` (upper-case key names, Feishu `APP_ID` / `APP_SECRET`), and the adapter reads no files itself; `http` = `transport`, `clock` = `clock`, `state` = `store`.
- **Feishu WS factory and status callback (P3 / P1d)**: the Feishu adapter's `transport` is the HTTP entry point; the WS client is injected separately through the constructor keyword `ws_factory` (tests pass a fake); by default `start()` imports lark-oapi via `require`, raising `channels.MissingDependency` if it is missing. Only Feishu has one extra optional keyword `status=` (separately: the Slack constructor also takes `ws_factory=None` / `sleep=time.sleep`, see "Slack specifics"; the `status(fields)` callback accepts only the fields `state / heartbeat_at / activity_at / error`, and `state` uses only `ok / reconnecting / needs_login / missing_dependency`); the actor uses it to write the status hash. **The signature of `base.Channel.__init__` does not change**, and other adapters do not add this parameter. A roster has at most one `type: feishu` (see the roster rules).
- **Send metadata (P0b)**: `Channel.fleet_name = ''` and `Channel.send_ref = None` are class-attribute defaults, **not constructor or `send_*` parameters, and never stuffed into `reply_ref`**. `fleet_name` = `channels.fleet_label(cfg)` (`name` → `token` → run directory name, same as `lifecycle_close.fleet_name`; no cfg or none of the three → `''`, never falling back to the account name), set by whoever constructs the channel: the resident actor (P1g), `send_direct` (P1e). `send_ref` = the logical request this send belongs to (the outbound item's `request_id`, or the item `id` if none); P1e sets it before each send and resets it to `None` in `finally`; all segments and retries of one item share the same value, and it never leaks into the next item. Adapters may read these two attributes (email puts them in the subject / headers, as P5 decides); other adapters may ignore them.
- **Unified push / pull inbound (item 2)**: pull-style platforms (Telegram getUpdates, WeChat getupdates, IMAP) fetch in `_poll(timeout)`; push-style ones (Feishu WS) start their own thread in `start()`, and the callback **only puts the raw event into the adapter's internal queue** (no I/O, no policy); `_poll(timeout)` blocks for at most `timeout` seconds to take it out. The actor has a single loop: `poll → inbound → mapping`. A button / card callback that must be answered synchronously (Feishu: a toast within 3 seconds) is answered on the spot by the adapter with a fixed toast (e.g. 「已收到」, "received"); the pressed command is queued as usual and the result is sent as a separate message; there is no synchronous `on_action` exit. Health: `health() -> {state, heartbeat_at, activity_at, error}`, `state` ∈ `channels.INBOUND_STATES` = `ok / reconnecting / retrying / needs_login / missing_dependency / conflict / rate_limited / stopped / outbound_only` (receiving channels default to `ok`; `retrying` = a transient inbound failure, cursor unchanged, refetch next round; unified in P0b — P0's old state names are retired with no aliases); credentials rejected by the platform (Feishu `ClientException`) → `needs_login`, stopping only this account's inbound (retried when the account file changes or every `config_retry_s`; see the process model), not treated as an ordinary crash to restart over and over, and never making the actor exit. Feishu card actions can only be received as the new `card.action.trigger` event (lark-oapi 1.5.3 WS drops CARD frames), which must be subscribed to in the developer console — this is part of P3's on-device acceptance steps.
- **Proxies are handled only per client, never by changing the process environment**: adapters must not `del` / `pop` / rewrite proxy variables in `os.environ` (other channels in the same process may need the proxy). How Feishu WS connects directly: swap exactly two things on the `lark_oapi.ws.client` module only — `requests` becomes a Session with `trust_env=False` (endpoint discovery), and `websockets` becomes a shim whose `connect(url, **kw)` calls the real `websockets.connect(url, proxy=None, **kw)` and forwards every other attribute; idempotent. HTTP sends use the proxy environment variables as usual. A contract test scans the `fleetmux/channels/` source and blocks any code that changes the environment.
- **Optional dependency isolation (item 6)**: adapter modules import only the standard library at top level; optional package names are listed in the class attribute `OPTIONAL_DEPS` (Feishu `('lark_oapi',)`) and imported only in `start()` via `self.require(module, pip)`; if missing, `channels.MissingDependency(package, hint)` is raised (a subclass of `channels.Unavailable`). **A module that fails to import does not count as isolated**: `channels.adapter_class` recording an `ImportError` as `Unavailable` is only for "that package has not landed yet"; an adapter with optional dependencies must still import normally when the package is missing, with standard-library sending still usable (Feishu without lark-oapi can still send text / cards / files with urllib), and the contract case first asserts that `adapter_class` succeeds. When the actor gets this, that account becomes **send-only**: sending works, `inbound = missing_dependency`, audit `channel.unavailable` (with the package name), and `channel status` / `channel test` print 「入站：未装 <包>（pip install …）；发送可用」 ("inbound: <package> not installed (pip install …); sending available"). The contract tests have one parametrized case: make the optional package unimportable; the module still imports, `start()` reports `MissingDependency`, `send_text` succeeds, and the `health()` state is valid.
- **Attachments (item 5)**: inbound files are downloaded by the adapter in `parse_inbound` (Feishu `GET /im/v1/messages/<message_id>/resources/<file_key>?type=image|file`) into `inbox_dir` (the actor passes `<run>/inbox/files/`), file name `<message_id with everything outside [A-Za-z0-9._-] removed>-<original name>`; over `MAX_FILE_BYTES` (20 MB) or an unrecognized type → not downloaded, goes into `rejected_files` (the actor replies with the rejection text). Downloads happen on the actor's `poll → inbound` thread, not on the WS callback thread, so they never hit the 3-second toast limit; there is no two-phase `fetch_file` interface: one envelope = one ready input. Outbound files go to the same conversation via `send_file` (Feishu first uploads to `/im/v1/files` to get a `file_key`).
- **Target and `reply_ref` (item 4)**: the target is passed explicitly as `send_*(conversation, …, reply_ref=None)`. Feishu `reply_ref = {"chat_id": "oc_…", "message_id": "om_…"}`: with a `message_id` it replies (`reply_in_thread` default false); without one (a proactive push has only `conversation = chat_id`) it creates a new message.
- **Error types and redaction**: on the inbound side (`_poll` / `_ack` / `start` / `check`) adapters raise `channels.ChannelError(kind, detail, retry_after=None)`, `kind` ∈ `auth` (e.g. 401) / `conflict` (e.g. Telegram 409: the token is in use elsewhere or a webhook is set) / `rate_limited` (e.g. 429, with `retry_after`) / `network` / `bad_config` / `transient`; `channels.Retryable` is the `transient` subclass (no acknowledgement, refetch next round). The base class records it as audit `channel.error` (with `kind`) and sets the `health()` state (auth / bad_config → `needs_login`, while the audit's `kind` stays `auth` / `bad_config` to give the reason; conflict → `conflict`, rate_limited → `rate_limited`, network → `reconnecting`, transient → `retrying`); the actor **reads only `health()['state']`** to decide backoff (`rate_limited` waits `retry_after`, `needs_login` at least 300 seconds) and **never parses the `last_error` text**; `needs_login` stops only this account (see the process model). A missing account file, a missing key or a malformed file is likewise `needs_login` (`kind = bad_config`). Sending always returns a `SendResult` and never raises. **Redaction `channels.redact(value, account=None)` (P0b)**: recurses through strings, dicts and lists; masks every value of ≥ 6 characters from the account file, the value of an `Authorization:` header, `Bearer <token>`, the `bot<token>` segment of a URL, Slack tokens (starting with `xoxb-` / `xoxp-` / `xapp-`, replaced by `***` including the prefix; P9a), values of secret-named fields in JSON form (`"context_token": "…"`, `"typing_ticket": "…"` and other keys whose names contain token / secret / password / ticket), the values of `qrcode=` / `verify_code=` / `qrcode_img_content=` in login URLs and of the URL parameters `key=` / `ticket=` / `sign=` / `signature=` / `auth=` (shared by all channels), `name=value` / `name: value` where the name contains token / secret / password, and string values in dicts whose key names contain token / secret / password / authorization — all replaced by `***`; numbers are kept (`{'tokens': 5}` is unchanged). `Channel.redact(text)` delegates to it (signature unchanged); the error strings of `Channel._fail` and **every field** of `Channel.audit` pass through it (the Telegram token is right in the URL, Feishu's `context_token` is in `reply_ref`), pinned by a parametrized contract case and `test_p0b_errors_and_audit_mask_account_values`. **409 does not trigger an automatic `deleteWebhook`** (that would change configuration elsewhere); it is only reported, and `channel test` also only reports it and leaves the decision to a person.
- **Telegram specifics (P2 implementation)**: `getUpdates` uses `allowed_updates = ["message", "callback_query"]`; `TEXT_UNITS = 'utf16'`, `TEXT_LIMIT = 4000` (UTF-16 units, conservative; the base class's `split_text(..., 'utf16')` never splits a surrogate pair); a card = one message with inline buttons, and **cards are never split** (an overlong body is truncated with 「…」, because the buttons must be on the same message for the bound message_id to be unique); `callback_data` = the button command verbatim (`/approve p-<8hex> <16hex>` is 36 bytes; **for a button over 64 bytes (`envelope.COMMAND_MAX_BYTES`), the Telegram adapter itself degrades the whole card to typed `card_text` commands and never truncates** (the length is Telegram's own limit, not a card rule — `card_problem` does not check length, and the base class's `send_card` passes it to `_send_card` as usual)); malformed `callback_data` is reported unchanged (envelope `text` = the raw string), and `parse_command` judges it `invalid` / `unknown` and replies with the reason; attachment files are created exclusively with `Channel.new_inbox_file()` (`O_EXCL`, same names get `-2`, `-3`), never overwritten, renamed or deleted; a file goes into `files` only when the downloaded byte count equals `file_size`; unfinished files are never referenced and stay on disk for a person to clean up (whether to clean up = undecided until v2); `SendResult.message_id` is interpreted by the adapter itself (cards: `"<chat_id>:<message_id>"`, for `update_card`).
- **Telegram media text and provenance (P8b)**: media with a `caption` → `text = ''` and `provenance` has **exactly one** segment `{kind: 'caption', text: <caption verbatim>}`; forwarded media yields only **one** `forwarded` segment (with the caption merged into it) and **no longer repeats** a `caption` segment; no label is added outside the segment text, so with no policy `wrap(env, None)` still yields the caption verbatim, the same as before P8. Media without a caption → `text` is a **closed constant label** inside the adapter (a sticker is exactly `[贴纸]` ("[sticker]"), pinned by an equality check in the migrated tests) with no `provenance` (empty by default); this item (U7) supersedes the older wording "`text` is non-empty (caption or label)"; **file names (`document.file_name` etc.), file_id and other sender-controlled bytes never go into `text`**, only into `rejected_files[].name` / the on-disk file name. Oversized or unsupported media behave as before: one `rejected_files` entry, `files` empty. The only migration of already committed tests is lines 409 / 410 of `tests/test_channel_telegram.py::test_oversize_or_unknown_media_goes_to_rejected_files` (`test-contract:`). The field shapes (`forward_origin` etc.) are offline contract assumptions not checked against official documentation; there is no claim that provenance detection is complete across all platforms.
- **TLS (all adapters)**: HTTPS, `SMTP_SSL` and `IMAP4_SSL` always use `ssl.create_default_context()` (certificate and hostname verification); `CERT_NONE`, `check_hostname = False`, `_create_unverified_context` and `verify=False` are forbidden, enforced by a contract test that scans the `fleetmux/channels/` source.
- **Outbound idempotency key**: every public `send_*` can take `key=` (the outbound queue item's `id`, the same on every retry of that item; None for direct sends); during the call it is `self.send_key` (`:<segment number>` appended from the 2nd segment on), from which an adapter can derive a stable platform identifier (email: `Message-ID`). Outbound delivery is **at least once**.
- **Two ways to handle overlong text (capability flag `OVERFLOW`)**: `split` (default) splits by `TEXT_LIMIT` / `TEXT_UNITS`; `file` (email) hands the whole text to `_send_long_text` when it exceeds `TEXT_LIMIT` (one message: a summary + the full text as a `.txt` attachment), without splitting. Contract tests branch on the capability rather than hard-coding 4000.
- **Email specifics (P5 implementation)**:
  - Envelope: `message_id = em:<UIDVALIDITY>:<UID>` (the account is already in the seen key), `conversation` = the sender address in lowercase, `reply_ref = {message_id, references, subject}`, `files[].path` is an absolute path. No cards: `send_card` goes through `card_text` (button commands written out as text), and `update_card` sends a follow-up mail (the base class already does this); `OVERFLOW = 'file'`, `TEXT_LIMIT` is set by P5 (proposed: 100 000 characters). Reply headers `In-Reply-To` / `References` come from `reply_ref`; the recipient can only be the conversation's allowlisted address, never the inbound `Reply-To`.
  - Injection: P5 defines `transport` as a factory callable (e.g. `transport('smtp' | 'imap')` returns a connection object); tests inject a fake SMTP / IMAP; `clock` is already a constructor argument; `_poll(timeout)` waits within `timeout` itself (IDLE or polling), and the actor stops between two polls, with no separate sleep / stop signal. The Python floor follows `deps.yaml` (3.14); IDLE uses what `imaplib` ships; when the server does not support IDLE, poll (`POLL_S`, default 60).
  - Account file (`channels/email-<account>.env`, never in environment variables): `ALLOW` (sender addresses, lowercase), `ADDRESS`, `APP_PASSWORD`, `SMTP_HOST` / `SMTP_PORT` (default `smtp.gmail.com:465`), `IMAP_HOST` / `IMAP_PORT` (default `imap.gmail.com:993`), `TRUSTED_AUTHSERV` (default `mx.google.com`), `IDLE` (auto / off), `POLL_S`, `MAX_FILE_BYTES`, `MAX_FILES`, `PUSH_TO`. **None of these are roster keys** (a roster entry still has only `type / account / push`), and there is no switch that relaxes validation.
  - Inbox cursor: `UIDVALIDITY` + the last acknowledged UID, kept in this account's store (the run's private Redis); **the same receive-acknowledgement semantics** as the Telegram offset ("Inbound acknowledgement" above): messages are handled one by one in ascending UID order, and `_ack` advances only after a deterministic rejection or once seen is recorded; transient failures (network, parsing, writing an attachment to disk, seen not writable) do not advance, and the round stops at that message. `UID SEARCH UID n:*` returns the largest UID even when there is no new mail, so filter again with `uid > last_uid`; fetch only `BODY.PEEK[]`; `\Seen` is not used for idempotency. **Persistence across runs is still undecided and the cursor lives only in Redis; the first run without a cursor and a `UIDVALIDITY` change are settled in P5b: reset to the current largest UID, no replay, audit `channel.cursor_reset` (see the email item under "Phase B additions" below) — not a silent skip; mail that arrived while stopped under the same `UIDVALIDITY` is still picked up from the cursor**.
  - Non-conforming body (HTML only, attachments over the limit / too many) = deterministic rejection: an envelope carrying `rejected_files` (the body is named `(正文)` ("body")) is persisted as usual and the actor replies with the rejection text; **body over `TEXT_MAX`** → no envelope (`parse_inbound` returns `[]`), audit `channel.drop_size`, no file written, no receipt (implemented in P5b); a partially written attachment stays on disk unreferenced and is audited as `channel.file_partial` (cleanup is undecided, v2).
  - **Sender authentication (`verified`; a conservative design, not yet verified against a live server)**: use only the **topmost** `Authentication-Results` header, whose `authserv-id` must equal `TRUSTED_AUTHSERV`; in it, `dkim=pass` with `header.d` (or the domain of `header.i`) equal to the From domain, **and** `spf=pass` with the `smtp.mailfrom` domain equal to the From domain; a `dmarc=` that is not pass → reject; From holds exactly one address. Any check failing → `verified = false` (the base class drops it by policy, no reply), and the adapter also records `channel.drop_auth` (reason: `no_trusted_ar / dkim_fail / dkim_unaligned / spf_fail / spf_unaligned / dmarc_fail`). **An AR header is just a mail header, not independent authentication**: any sender can write one and even copy the `authserv-id`. The **trust premise** of this check is that the receiving service, per RFC 8601 §5, strips (or renames) foreign AR headers that carry its own authserv-id and puts its own AR on top, and that mail is received only through that service, with no intermediate forwarder adding an AR before it. **These premises are not yet verified**: acceptance on a live account after delivery must send mail with a forged AR to test whether Gmail strips it; until then, docs and reports may only say "verdict based on the trusted receiving server's AR, relying on it to strip forged headers", never "spoof-proof". Offline tests only prove the parsing and decision logic.
  - **Body and commands (P8b)**: "body" means the cleaned body B (quotes, signature and leading / trailing whitespace removed; not the raw MIME). **Only when B is exactly one line starting with `/`** does B stay in `text` for `parse_command` to recognise as a command (no `provenance` entry); **a multi-line B is always data**: `text=''`, `provenance=[{kind: 'email_body', text: B}]`, **even if its first line starts with `/`**, so forwarded or quoted commands cannot be triggered through mail. This is an explicit rule, approved as a **deliberate change to the old command routing when there is no policy**: before P8b a multi-line body whose first line was `/…` was treated as a command by its first word (or `unknown_command`, not delivered); after it, it is delivered to the supervisor as ordinary text; **this case is not claimed to be unchanged from before P8**. Everything else is unchanged: an ordinary body is delivered verbatim through `wrap(env, None)` (no strip, same rule as the inbound delivery text), and a single-line `/command` still goes through command recognition.
- **`reply_ref` is a sensitive opaque value**: only the adapter that produced it reads and writes it (WeChat `context_token`, Feishu message_id, email Message-ID…); upper layers only store it as-is in the run's private Redis (`fx:channel:origin:*`, `fx:channel:last`, the account store) and hand it back to the adapter unchanged. **It never goes into any audit, log, `channel status` / control, supervisor message, exec stdin, or any file other than `state/last.json`**; the base class's own audit never carries it.
- **One rule for invalid credentials**: when the platform rejects credentials (Telegram 401, an expired Feishu token, WeChat `errcode = -14` session expired), the adapter always raises `ChannelError('auth', …)` → `health()` is `needs_login`, audit `channel.error kind=auth`, `channel status` shows "需重新 channel login <type> <account>" ("run channel login <type> <account> again"), only this account stops, and it retries when the account file changes (or every `config_retry_s`) — **no endless retries**, and the actor does not exit.

{"channel": "telegram", "account": "fleet-bot-1", "conversation": "<chat id>", "message_id": "tg:<msg>:<chat>",

**Commands (`envelope.parse_command`, purely deterministic)**: `/status`, `/help`, `/approve <pending id> [<nonce>]` (without nonce = step one, `approve.handle_command` replies with a confirmation card; with nonce = step two, confirm), `/reject <pending id> [reason]` (one step), **`/stop [reason]`** (P8a: `{kind: 'stop', reason}`, handled directly by the actor, never goes to the supervisor, see "Security pack"); the third argument of `/approve <pending id> <nonce> <6 digits>` → `code` (P8a reserves it for P8l's TOTP; any other shape → `invalid`; 43 bytes); pending id `p-` + 8 hex digits (`envelope.PENDING_ID_RE`), nonce 16 hex digits (`envelope.NONCE_RE`); `/approve p-<8> <16>` is 36 bytes in total. **Inbound mapping (P1d actor)**: ordinary text → `runtime_v2.post_event(kind=operator_input, agent=supervisor, generation / thread = current value of fx:agent:supervisor, run_id, text, request_id=<related id>, source='channel:<type>:<account>')` → `wait_reply` (**`text` = the finished body of the delivery text described below, verbatim**: no strip, not the `cmd['text']` normalised by `parse_command`; `parse_command`'s whole-string `.strip()` contract is unchanged and **used only for command recognition**) → receipt according to the answer; **after acceptance (`accepted`) the actor writes `fx:channel:origin:<id>` (EX 7 days), `fx:channel:last`, and the mirror `state/last.json`**; rejected / unconfirmed → receipt and `forget()`. The event carries no extra fields such as origin (no added privileges). `/status` reads only the same data as `control_view.snapshot`; `/approve` `/reject` go to `approve.handle_command` (P6b).

**Inbound acknowledgement, idempotency and replay boundary (`base.Channel.poll / inbound` implemented and pinned by P0 cases)**

1. **Platform cursors (Telegram offset, WeChat `get_updates_buf`, IMAP UID) advance only after an entry is "final"**: the base class handles entries one by one in platform order; a raw entry is final only once all its envelopes are settled, and then the adapter's `_ack(raw)` advances the cursor. There are only two kinds of final: **deterministic rejection** (not a private chat, outside the allowlist, unauthenticated, malformed, a type outside `allowed_updates`, file too large / of an unknown type — the latter is accepted as usual as an envelope carrying `rejected_files`); **reliably received** (the actor's `accept` answers `persisted` or `duplicate`).
2. **Transient failures do not advance**: `parse_inbound` raises `channels.Retryable` (attachment download network error / 5xx), `accept` raises anything (seen cannot be written to Redis), or `_ack` itself fails — this entry and those after it in the batch are not acknowledged (order is kept) and are fetched again unchanged next round; those already received get `duplicate` from `accept`. Audit `channel.inbound_retrying` (no body), `health()` state `retrying`. **No retry cap, no dead-lettering, no self-reclassifying as a rejection** (whether to cap, who decides and where dead letters go are undecided, v2); one stuck entry blocks the messages behind it until the fault clears.
3. **seen is only a dedupe claim, not reliable receipt**: `seen:<message_id>` (this account's store, `SET NX`, `SEEN_TTL`) only prevents the same entry from being processed twice; **the cursor advances only after the fleet answers** (item 4). On the actor path the only writer of this key is `actor.handle_inbound` (as the `accept` callback); the base class's default `accept` (same key) is only for paths that bypass the actor, and the two never stack; `duplicate` means the same `message_id` has already been fully processed. **There is no inbox stream.** The `message_id` an adapter produces must be stable for the same platform entry (Telegram `tg:<message_id>:<chat_id>`, callbacks `tg:cb:<callback_query.id>`).
4. **Deliver to the fleet first, then acknowledge the cursor (P1d seam)**: the actor calls `ch.poll(timeout, accept=<handle_inbound callback>)` / `ch.inbound(raw, accept=…)`, **not** `poll(accept=None)` to get envelopes and process them afterwards. For each envelope the callback: claims seen with `SET NX` (already there → `duplicate`) → local deterministic commands / rejections (`/status` `/help`, unknown / bad arguments, too long, `rejected_files`, a Codex supervisor that takes no mid-turn input) get their receipt and answer `persisted` → otherwise post `operator_input` (event id = request id, derived deterministically from `<type>:<account>:<message_id>`; `post_event`'s producer key makes reposting the same entry a no-op), `wait_reply`: accepted → write origin / last, receipt, answer `persisted`; the fleet explicitly rejects → receipt, `forget()`, answer `persisted` (deterministic rejection, the cursor moves past it); unconfirmed (timeout) or error → `forget()`, raise `channels.Retryable`; this entry and those after it in the batch are not acknowledged, are fetched again unchanged next round, and are posted / awaited again with the same request id. Only `persisted` / `duplicate` make an entry final and let `_ack` advance the cursor. **Replay boundary**: within the seen TTL, one `message_id` becomes at most one fleet request / instruction; entries the platform cursor has moved past are never fetched again automatically (a user resend is a new message). `/approve` `/reject` also go through `handle_inbound`, and `approve.handle_command` is idempotent per `message_id` (P6b). **Generation conflict**: when an event with the same request id was already posted and, after a generation change, the content differs and no answer can be found, the receipt is the `unconfirmed` text plus a new line "上次投递结果未确认，本次无法重投。" ("The last delivery's result is unconfirmed; this one cannot be redelivered."), followed by the same `forget` + `Retryable`, no ack, no redelivery; this sentence is the actor constant `actor.NO_REDELIVERY`, **not part of `envelope.RECEIPTS`** (there is no `contract:` receipt entry for it).
5. **Side-effect hooks**: `on_accepted(env, outcome)` (Telegram: `answerCallbackQuery` with "已收到" ("received") after persisting), `on_dropped(env, reason)` (Telegram: an empty answer); hook errors are only audited and change neither the result nor the cursor. For push-style channels (Feishu WS) the callback thread only puts raw events into a queue; for platforms that need no acknowledgement `_ack` is empty.
6. The base class's `forget()` is the rollback of the actor path: when the fleet did not accept, it deletes the seen key in this account's store so the next fetch can try again (P1d). Envelopes returned by `poll` on the actor path are already fully processed; the actor does not process them a second time.

**Outbound item (`envelope.outbound`; also the JSON on the exec channel's stdin)**

```json
{"id": "out-<hex>", "event": "result", "target": "origin", "request_id": "ui-…",
 "channel": "", "account": "", "conversation": "", "reply_ref": {},
 "text": "…", "card": null, "file": null, "caption": "", "update": null, "user_only": false, "at": 1762650000.0, "attempts": 0}
```

- `event` ∈ push events + `reply` (inbound receipt) + `manual` (manual `channel send`); exactly one of `text / card / file`; `target`: `origin` (look up the origin via `envelope.origin_id(request_id)`: `<id>.done` looks up `<id>`'s, for P7 sub-fleet follow-up pushes), `last` (the most recent interaction; falls back to first), `first` (the first channel in the roster with `PUSH_TO`), `explicit` (channel / account / conversation all given). No conversation found → audit `channel.no_target`, not sent. `user_only`: sent only to a conversation in which an allowlisted user has chatted privately in person (delete-approval cards). `update`: id of the card message to replace. Over-long results (more than 3 segments) are sent as a file: the file is written under the directory given by the optional keyword `outbox` of `actor.outbound_scan(r, entries, *, clock=time.time, outbox=None)` (the actor passes `<run>/outbox`; None = `config_dir()/state/outbox`), plus a short text message.
- Card (`envelope.card`): `{title, text, buttons: [{label, command}] ≤ 6, ref}`; button commands start with `/`.
- Push event sources (P1 outbound watch): `result` ← entries in `fx:results` / `fx:result:<id>` whose origin is found via `envelope.origin_id(result id)` (including `<id>.done`; if not found and the result is younger than `ORIGIN_GRACE_S`, check again next round); `task_done` ← `fx:task` entering completed / blocked / budget_exhausted; `prompt_wait` ← outbound items written by the daemon side (P6); `escalation` ← new `dialog:` / `blocked:` entries in `fx:escalations`; `run_closed` ← `lifecycle_close.notify`, plus a second source: the daemon's explicit stop tail (`RuntimeV2.run`), which, when cfg has `channels` **and `not lifecycle_close.managed(f)`**, LPUSHes an item `event: run_closed, target: last` (dedupe key `pushed:run_closed:<run_id>`) — runs with a lifecycle go through `notify`, never both; `escalation` is notice text only, no buttons, off by default; `daemon_down` ← `channel send --event daemon_down` from the "Daemon down" section of the supervisor's AGENTS.md. Each event is pushed only to channels whose `push` lists it: the conversation target (origin / last / first, chosen only among channels that can receive) gets one copy; outbound-only channels (exec, `CARRIES_TOKENS = False`) whose `push` lists the event each get another copy, with cards always passed through `envelope.redact_card` first (buttons and ref removed). `user_only` items (delete-approval cards) go only to the conversation target, which must be a conversation where an allowlisted user has chatted privately in person, never to outbound-only channels (exec gets only the one-line notice, with no pending id and no nonce, pushed separately when the approval record is registered). Dedupe key `fx:channel:pushed:<event>:<id>`. Rate limiting / dedupe / storm merging keys live under `fx:channel:throttle:`.

**User exit for delete-confirmation dialogs (P6①)**

- **Scope**: only the terminal dialogs of the `docs/design.md` §24 delete category (Claude / Codex / pi panes, the path where the watchdog captures the screen); whether opencode / dsh delete-type permission requests are covered is left to v2 (the three gates currently hard-code "delete-type requests are never answered by the fleet" and are not in the P6 file list), so for now the phone only receives notices for them. **A run without `channels:` writes no `fx:channel:pending*` keys, and slot fields and the audit sequence are unchanged.**
- **Registration** (P6b / P6c; daemon-side delete-type `prompt_wait`): `RuntimeV2.push_user_dialog(slot, rec)` calls `channels.approve.register(...)` to write `fx:channel:pending:<p-id>` (fields in the key table; the old record is marked `stale`), and LPUSHes a neutral card with `event: prompt_wait, user_only: true` (`approve.card(rec)`: fleet, slot label, generation, command and path, last 15 lines of the screen tail; buttons "批准" ("approve") `/approve <p-id>` and "拒绝" ("reject") `/reject <p-id>`) plus a one-line notice without id for outbound-only channels. `prompt_wait`'s existing pause, notice card and zero keypresses all stay as before.
- **Consent keys come only from explicit registration**: `keys_approve` is taken only from the `keys` of entries registered for this kind of dialog in the `watchdog_prompts.user_approve` section of an explicit `--prompt-table <file>` (`prompt_table` in the run's `config.json`); the section is optional and **empty by default**; `fleetmux/config/fleet.yaml` is **not extended**, and neither is what the private `~/.fleetmux/fleet.yaml` may override (it still may not override `watchdog_prompts`). Entry `{name, match: [...], keys: [...]}`: `match` is an explicit match condition written by the operator and may include the cursor text on screen (e.g. `"❯ 1. yes"`); `keys` ⊆ `watchdog.KEYS`; the program **never** infers keys from `watchdog.YES_CURSOR` and never adds Enter on its own — `keys_approve` comes only from the matching entry's `keys`. No matching entry (the default) → the card has **no "批准" ("approve") button**, only "拒绝" ("reject"; Escape, the safe direction), and says "没有登记的同意键，请在电脑上处理" ("no consent key registered; handle it at the computer"); even if someone assembles both `/approve` steps, zero keys are pressed: the watchdog's `answer_user` marks the record `stale` and presses nothing (implemented in P6c; no `result = no_key` is written); with a registration, positive approval works as usual and the seven pre-press checks are unchanged. `user_approve` is read only by the user path (registered pending items); the program path (`check`'s allowlisted keypresses) and the supervisor path (`answer_dialog`) never read it. Extending `watchdog.parse_table` / `TableCache` (schema validation, hot reload, auditing bad changes as `watch.table_rejected` and keeping the old table) belongs to **P6c**. The earlier proposals "put it in `config/fleet.yaml`" and "fall back to `YES_CURSOR`" are void and must never be used.
- **Two-step confirmation, one-time nonce**: step one `/approve <p-id>` (no nonce) → actor `handle_inbound` → `approve.handle_command(r, env, cmd, *, post, reply)`: allowlisted sender + `private` + `verified` (guaranteed by the base class) + record `pending` + not expired → `confirming`, generate a nonce (16 hex digits; only `nonce_hash` is stored), `confirm_until = now + approve_confirm_s`, record step one's `sender` / `conversation`, reply with the `confirm_delete` card ("确认删除" ("confirm delete") `/approve <p-id> <nonce>`, "取消" ("cancel") `/reject <p-id>`). Step two `/approve <p-id> <nonce>` or the rejection `/reject <p-id>`: `handle_command` posts through `post` the event `{kind: 'dialog_user_answer', pending_id, decision, nonce, channel, account, sender, conversation}` (P8kl adds the optional key `code`: present **only** when the command has a third argument (`/approve <p-id> <nonce> <code>`, totp), absent otherwise) (`post` = the actor's `post_event` + `wait_reply`) → a new branch in `Fleet.handle` → `RuntimeV2.user_dialog_answer(ev)`: the nonce's sha256 matches (for approval), the state is right, `confirm_until` / `expires` not passed, `sender` and `conversation` the same as in step one → `status = answered` + `decision`, answer `{status: accepted}`; otherwise answer `{status: stale, reason}` and leave the record unchanged. Reply `answer_taken` / `pending_gone` / `changed` according to the answer. A nonce is void once used.
- **Time limits (approved by the supervisor: configurable positive defaults in the run's `config.json`)**: the confirmation step `approve_confirm_s` = 120 s, the whole record `approve_ttl_s` = 1800 s (`channels.APPROVE_CONFIRM_S` / `APPROVE_TTL_S`; keys of the same name in the run's `config.json`, must be positive, written from the defaults by `start`; **X9: `approve_ttl_s` and `approve_confirm_s` are always run `config.json` keys, never in `security.yaml` / the security policy, and the chained policy composition (`effective_policy`) does not merge them either**). **Config validation (non-positive / non-numeric values rejected) and the actual expiry behaviour are delivered v2 test-first**; P0 freezes only the key names and defaults. Any expiry is **fail-closed**: no keys pressed, `expired`, reply with the `expired` receipt, and the dialog is left for the person at the computer.
- **Key press** (P6c: the watchdog's next tick runs `answer_user`, modelled on `answer_dialog`): recapture the screen; wall gate; generation / thread / scope / pane ownership / not adopted; same dialog; same screen-tail digest; still delete-type — press only when all hold: approval presses only `keys_approve`, rejection presses Escape, and only keys in `watchdog.KEYS` are sent; any mismatch → no press, record `stale`, reply with the `changed` receipt (changed, look again) (if the dialog is still there and still a delete → register a new record). If the person at the computer answered first (the transcript moved) → record `done`, and a late phone answer gets the `pending_gone` receipt ("已不存在 / 已被别处答掉": gone / answered elsewhere).
- **No automatic resume of dispatch**: after the keys are pressed, `prompt_wait`'s pause stays as it is; the `answered` receipt says the keys were pressed, the fleet is still paused (with the reason), and to resume use resume in control or run `fleetmux resume --config <run>/config.json` (existing entry points). **The earlier `channel_user_resume` auto-resume proposal is void**: no automatic resume has been authorised, this phase defines no auto-resume value for that config key, and `resume()` is never called after keys are pressed.
- **Audit**: `dialog.user_answered` (`pending_id, slot, generation, decision, channel, account, sender, checked, reason`); refused inbound (wrong nonce, expired, a different person or conversation in step two, wrong record state) is recorded as `dialog.user_refused`; an answer check that fails unexpectedly approves nothing, answers `stale` and is recorded as `dialog.user_answer_failed` (`pending_id, error`); non-allowlisted senders / group chats are silently dropped per the general policy + `channel.drop_policy`. **Neither audit carries the nonce, nor the nonce's hash.**
- **The nonce does not leak**: the raw nonce appears only in the confirmation card's buttons sent to an allowlisted user's private chat and (for channels without buttons) in the card text; it never goes into the `execution.prompt_wait` audit, the notice card, supervisor queue messages, any audit, log, `notifications.jsonl`, exec's stdin (the base class runs `redact_card` first for channels with `CARRIES_TOKENS = False`), or `channel status` / control.
- **Entry points**: step one only via the account actor's inbound path → `approve.handle_command`; step two / reject only via the `dialog_user_answer` event → `RuntimeV2.user_dialog_answer`, which accepts nothing without the correct nonce (when approving), the same sender and conversation, and a record still within its validity. **The delete dialog (`kind=dialog`) has no CLI entry**: no `fleetmux channel approve` is added for it (P8kl scope: this sentence covers `kind=dialog` only; P8l's local `channel approve` accepts only records with `kind=action` + `tier=high` + `confirm.high == desk` and refuses everything else, see "High-tier out-of-band methods"); `channel send` with `/approve …` text just sends a message; `/approve …` typed in the supervisor pane goes `claude_prompt → operator_input` and is plain text (`/word` is not queued); the `escalations` of the supervisor's decision JSON only accept `dialog:` / `blocked:` (and `split:`, P7), and an answer to a key shaped like `fx:channel:pending:*` is refused by `parse_service_decision`. P6b / P6c pin this with tests.
- **Security boundary (stated as is, no more)**: the above only shows that **the existing interfaces offer no path**. Separate keys and one-time nonces guard against mis-taps, crossed records and replay; they are **not** a security boundary against processes of the same user: supervisor / worker / daemon run as the same OS user, Claude slots are not sandboxed, and they can connect to the same Redis socket and read the same run directory and process memory, so forging an answered record or reading a nonce cannot be stopped. The residual risk is recorded in `docs/design.md` §53 "Known gaps"; we do not claim that "Redis isolation alone prevents programmatic approval".

**Direct to a worker (a Slack or other channel caller can talk to a worker directly instead of always going through the supervisor; see `docs/design.md` §53 "Direct to a worker")**: this changes the mapping "plain text = operator input":
- **Mention**: text the user typed by hand (`text`, never outside content) starting with `@<worker>` or `<worker>:` / `<worker>：` (the name ends in `-<digits>`, optionally with `.<generation>`, `actor.parse_address`) → the name is stripped and the rest is sent as one service request `{id: request_id(origin), to: <worker>, payload: {message}, instruction: actor.DIRECT_INSTRUCTION, reply: {required: [reply], allowed: [reply]}}` (`actor.submit_direct`: `post_event(kind=request)` + `wait_reply`, idempotent via the producer key; not marked `operator`, the supervisor neither takes part nor receives a relay). Accepted → origin / last written as usual, receipt `direct_accepted` (with `DIRECT_BUSY` when the worker is not idle at that moment); refused by the fleet (no such name, retired) → receipt `rejected` with the fleet's reason (including the list of names that can be dispatched to), not forwarded to the supervisor. `handle_inbound(..., direct=None)`: no direct route bound (non-service fleet, direct callers) → receipt `direct_unavailable`, not forwarded.
- **Thread ownership**: new key `fx:channel:thread:<type>:<account>:<thread root>` = worker slot name (without `.<generation>`), `EX ORIGIN_TTL`. Written in two places: when a direct mention is accepted (thread root = that message's `reply_ref.thread_ts`); when an outbound push carries a result a worker answered (thread root = the origin's `reply_ref.thread_ts`; not written for supervisor self-answers `worker=supervisor` or split delegations `result.delegated`). An inbound envelope with `reply_ref.in_thread` true whose thread root has an owner and no mention → direct to that worker; a mention wins; no owner → to the supervisor as before. Channels without threads (`reply_ref` has no `thread_ts`) are unaffected.
- **Hint line**: `outbound_scan(..., workers=None)`; the actor passes this (service) run's worker slot names (read from config.json, follows roster hot reload). Each pushed result gets one more line at the end: for a worker's answer `在本帖里回复 = 接着找 <worker>；新消息开头写 @<名> 直接派活（可点名：…）` ("reply in this thread = keep talking to <worker>; start a new message with @<name> to dispatch directly (names: …)"), for a supervisor's answer `要直接派活，消息开头写 @<名> 之类（可点名：…）` ("to dispatch directly, start the message with @<name> or similar (names: …)"). Empty `workers` → no line.
- **Results also go to the conversation**: an outbound `result` item whose `reply_ref` has `thread_ts` is sent with `broadcast: true` (Slack `reply_broadcast`); other events are not. Outbound items other than `result` / `reply` (the `prompt_wait` card, `task_done`, `daemon_down`, `run_closed` …, mostly sent to `last`) drop `thread_ts` / `in_thread` and are posted at the top level of the conversation, not into the thread the user last spoke in.
- **Slack envelope**: `reply_ref = {channel, thread_ts: <thread root>}`, thread root = the event's `thread_ts`, or the message's own `ts` when absent (every receipt / result goes into the thread under this message); replies inside a thread also carry `in_thread: true`. (The earlier rule "top-level message `reply_ref = {channel}`" is replaced.)
- New receipts `direct_accepted` / `direct_unavailable`; the `help` text gains two sentences on mentions and threads.

**Handing large jobs to a task sub-fleet (P7; reuses the existing mechanism of `docs/design.md` §44 instead of writing a parallel split path)**: P0b only registers the interface; no P7 code.

- **Reuse §44**: a service worker's split request is exactly §44's escalate answer `{"escalate": "<why>", "proposal": [{"id", "instruction", "output", "kind"}, …], "workers": n}`. Recording and validation, the `[escalate]` notice (`escalate_check` / `escalate_intake`), the supervisor's decision (`escalation_decision` / `escalation_apply`: approve may carry `supervisor_profile` / `worker_profiles`, and when it does, a `rotating` generation change happens before adoption), the accepted / rejected branches of `escalation_tick`, and adoption via `subfleet.request → process_requests → spawn_child` all call the §44 / §20 implementations directly. P7 adds only what the service side lacks: receiving the escalate answer (the `runtime_v2` service settlement branch), closing out the original request as `delegated`, the `<id>.done` follow-up result, and the `split_budget_h` time limit.
- **Number `M<n>`**: assigned by the program only when a service escalate answer arrives (`next_item_id`), writing `fx:items[M<n>] = {to, instruction, request}`; the ids of the proposal blocks are rewritten to `M<n>.<i>`; ordinary service dispatches get no number. **A finished split keeps its M row** (P7b): as long as the `sub/M<n>` directory exists, the number is not assigned again and `sub/M<n>` is never reused (otherwise the next split would get the same M number and its sub-fleet would land in `sub/M<n>-attempt-2`); a split that never started a sub-fleet (revise / reject / stale) releases its M number as before.
- **Supervisor decision key**: `escalations[].task = "M<n>"` (`parse_service_decision` accepts the `M<n>` shape; `dialog:` / `blocked:` as before), `decision` ∈ approve / revise / reject (as in §20 / §44), optionally with `workers`, `note`, `supervisor_profile`, `worker_profiles`; revise may omit note (as in §44, not counted as a consecutive refusal).
- **Who decides**: config key `split_judge` ∈ `worker` (default; the worker decides and sends an escalate) / `off` (split requests are refused, with the reason stated); "decided by the supervisor at dispatch time" has only a reserved parameter slot in this phase.
- **When and how the request closes out (the result status set is unchanged)**: the original request closes out **on the tick in which `escalation_tick` reads the spawn answer `accepted`** (not at the moment of approval; spawn `rejected` → the request goes back to `escalated` awaiting approval and the request stays `dispatched`), with the existing status `ok`, `result = {"reply": "已转 task 子 fleet M<n> 处理；子 fleet 结束后另发结果 <id>.done。", "delegated": "M<n>"}` (reply: "handed to task sub-fleet M<n>; the result is published separately as <id>.done when the sub-fleet ends"). `delegated` is just a key in `result`; the status set is still `ok / invalid / skipped / timeout / stalled / failed / blocked / rejected`, nothing added. On parent `start --resume`, accepted requests are settled before requests are replayed (`Fleet.split_settle_accepted()`); a request whose original request is gone is recorded as `split.stale` and deleted.
- **Sub-fleet**: a split sub-fleet has `lifecycle=None` (does not use `child_lifecycle`'s `dev_task`); the child config does not inherit the parent's `channels`; time limit = `limits.split_budget_h`.
- **Follow-up result `<id>.done`**: when the sub-fleet is collected (or fails to start), P7 calls `publish("<id>.done", "ok" | "failed", …)`: `ok` carries `result = {reply, delegated, run, outcome}`, `failed` carries `error` (same shape as existing failed results). **`subfleet.collect` returns immediately and does nothing for a record already collected (status not in ACTIVE: returned / failed / down)** (P7b): production call sites (`tick`, `stop_children`, `resume_children`) pass only ACTIVE sub-fleets; collecting an already-collected record again would restart slots that are already doing something else. The record has the same shape as `fx:result:*` and is also RPUSHed to `fx:results`.
- **`.done` is a reserved id (P7b)**: `<rid>.done` is only for the delegated request `<rid>`; `Fleet.request` refuses external requests named `<rid>.done` (P7b only adds in its own branch, changes nothing; `fleet.REQ_ID_RE` is unchanged); if `fx:req:X.done` / `fx:result:X.done` / its public tombstone already exists at approval time → approval is refused (a program reason, not counted).
- **Idempotency**: `X.done` is published only once, reusing the existing public tombstone of `runtime_v2.publish` (a second publish of the same id returns immediately); no new mechanism. The channel-side dedupe key is `fx:channel:pushed:result:X.done`, so an actor restart / rescan does not push again.
- **The origin covers both the original request's result and the follow-up result**: the actor writes the origin into `fx:channel:origin:X` after the original request is accepted (a separate key, not lost when `publish` deletes `fx:req`). The outbound watch uses `envelope.origin_id(result id)` for every result: `X.done` → `X`, any other id → itself; a push item's `request_id` = the result id (e.g. `X.done`), and `resolve_target` uses `origin_id` to find `X`'s origin. A `failed` follow-up result is pushed too. P1 must not filter results by "id contains a dot".
- **Origin lifetime and the sub-task budget**: the origin has `EX` 7 days from acceptance; `split_budget_h` defaults to 4 hours, far less than 7 days, so every follow-up result finds the original conversation; with a budget above 7 days, an `X.done` after expiry finds no origin and, under the 60-second grace rule, is treated as an external result and not pushed. P7 touches no `fx:channel:*` key.
- **`limits.split_budget_h`**: positive integer hours, default 4, configurable: root config `limits` and root roster `limits:` (hot reload, like the four limit keys of §19); `roster.parse_limits` accepts this key (one more entry in `LIMIT_KEYS`, added by P1a on behalf of P7); sub-fleet time limit = this value; the other limits (`max_depth / max_children / max_agents_total / child_workers_max`) are unchanged.

**Process model (C13: one actor per fleet; approved by the supervisor)**: **one actor child process per fleet**, `fleetmux channel actor <config.json>` (internal subcommand), a child of the daemon and supervised by it (`Fleet.channel_tick`, P1f).

- **What the actor does**: takes a lease for each `type:account` in the roster (`lease.acquire_all`; for an account whose lease is taken, audit `channel.lease_busy` with the holder, status `lease_busy`, stop only its inbound, retry every `lease_retry_s`) → reads the account file, builds the adapter, `start()` (`MissingDependency` → that account sends but does not receive; credentials missing / bad / rejected by the platform → that account's state is `needs_login`, receiving stops until the account file changes or every `config_retry_s`) → one inbound thread per account (`poll → inbound → handle_inbound`); outbound: watch (`outbound_scan`: `fx:results` / `fx:task` / `fx:escalations` → `fx:channel:outq`, dedupe via `pushed` keys) → route (`resolve_target` + `queue.route` → `fx:channel:outq:<type>:<account>`; not found → `channel.no_target`) → **each account's own outbound queue** does rate limiting / sending / retries / dead letters; a separate thread writes the `fx:channel:actor` heartbeat every `channels.BEAT_S` (10) seconds, and each account's `health()` is written into the status hash after every inbound round. **A failing account stops only that account: the actor does not exit, other accounts are unaffected, the fleet is not paused, no slot is charged.** Parent daemon gone (judged only by a change in `os.getppid()`, `supervise.ParentWatch`; `daemon.lock` is not probed) → exit within 5 seconds and release all leases. On SIGTERM → drain the outbound queues for up to 5 seconds, then exit.
- **What the daemon does** (no network I/O; exceptions are caught separately and written to `tick.error`; a channel never stops the fleet): starts / supervises this one actor process (`channels.actor.Supervisor`, implemented in `supervise.py`, re-exported in one line from `actor.py`): after an exit, backoff starts at 30 seconds and doubles, capped at 5 minutes, reset after 10 stable minutes (`channel.actor.restarted`), and after 5 consecutive failures it only alerts (`channel.actor.failing`); on an explicit stop, after `run_closed` is queued it calls `Fleet.channel_stop_all(drain_s=5)`, giving in-flight sends a bounded drain window before Redis closes; a timeout does not block shutdown. No launchd / cron; a roster hot reload that changes `channels:` → restart the actor.
- No adapter module or optional dependency is imported in the daemon process; the direct send (`send_direct`) of `channel send` / `lifecycle_close` builds a single adapter in the caller's own process, sends only, never receives, takes no lease. lark-oapi 1.5.3 can run only one Feishu WS per process, so a roster has at most one Feishu entry (added to `parse_channels` in P0b).
- **Invariants**: the daemon does not import adapters; no single channel failure **pauses the fleet or charges any slot**, it only audits / alerts; `send_direct` sends only, never receives, never grabs the inbound lease; **by default a run without `channels:` starts no process, writes no `fx:channel:*` key, and behaves exactly as before** (P1 uses `channels.actor.plan_processes(cfg, config)` to give the processes to start: exactly one argv when `channels:` is present, ending in `channel actor <config.json>`; an empty list otherwise). `channels.ACTOR_EXIT_CONFIG` / `ACTOR_EXIT_LEASE` are only reserved names: with a single actor, no account can make the actor exit with 3 / 4.
- **Supervision timings (configurable defaults)**: can be overridden key by key with the `channel_supervise` object of run `config.json`; keys and defaults = `channels.SUPERVISE_DEFAULTS`: `backoff_start_s` 30, `backoff_cap_s` 300, `stable_reset_s` 600, `failing_after` 5 (supervising the actor process); `lease_retry_s` 300, `config_retry_s` 600 (retries of a single account inside the actor); missing keys take the default; bad values (not positive) are refused by the config validation of `start` / the daemon, like other config keys. `channels.actor.Supervisor(spawn, clock=time.time, settings=None, *, audit=None, beat=None, stale_s=90, grace_s=90, stop_wait_s=5)` uses the defaults when `settings` is not passed (the actual P1f signature).

- **Hard stop `/stop` (P8m; Z1–Z11, #17; security freeze batch 2)**: when the actor receives `/stop` it writes the `fx:service` pause and `fx:channel:stop` through `PUBLISH_LUA` and replies with the receipt `stopped`, without going through the supervisor; the daemon's `security_tick` acts by level (`interrupt` / `kill` press Escape on this fleet's own worker slots with `state ∈ {busy, starting}`, `kill` additionally takes the explicit stop path; `pause` presses no key). The items below are frozen text:
  - **Z1 stop epoch**: the stop epoch = field `stop_epoch` of the existing hash `fx:service` in the run's private Redis: a non-negative decimal integer, shape `^(0|[1-9][0-9]{0,15})$` and `< 2^53`, default (field absent) 0; **it is incremented only by P8m's `PUBLISH_LUA` with `HINCRBY fx:service stop_epoch 1`, only ever goes up, and has no TTL**; `Fleet.pause()` / `resume()` and the other writers of `fx:service` neither read nor write this field, so old epochs stay void after `resume`. No separate `fx:channel:stop_epoch`. Readers: `approve.py` (compares at register / issue / consume) and P8i through it. A malformed shape (non-integer, leading zero, sign, ≥ 2^53) always fails closed: a P8m publish returns `invalid` with zero writes; the approve side refuses. **D3 (recorded, not fixed)**: a P8m publish reports a malformed epoch by the item names the tests pin — a bad `fx:service.stop_epoch` → `{'invalid', 'stop_epoch'}`, a bad `fx:channel:stop.epoch` → `{'invalid', 'stop.epoch'}` (i.e. Z5's `<item name>`); the approve side still reports the reason `epoch_malformed`, see C5 under "Action confirmation".
  - **Z2 `fx:channel:stop` fields (X14: adds `id / reason / epoch / rank`)**: `fx:channel:stop` is a hash (type unchanged) meaning "there is an unprocessed `/stop`". Fields: the frozen `level` (`pause` / `interrupt` / `kill`), `by` (`<type>:<account>:<first 4 chars of sender>`), `at` (seconds, float); **added** `id` (32 lowercase hex chars, the most recently merged request id), `reason` (≤ 400 chars, `channel stop by <by>: <reason>`), `epoch` (the Z1 value at the latest publish), `rank` (1 / 2 / 3 for pause / interrupt / kill). No TTL. Consecutive `/stop`s that arrive before the daemon handles them are merged: `level` / `rank` take the stronger one, `id / by / at / reason / epoch` take the latest. Only `PUBLISH_LUA` writes it and only `RELEASE_LUA` deletes it (delete by comparing `epoch`); the actor never deletes it. approve's REGISTER only checks whether it exists.
  - **Z3 `fx:channel:stop_req:<id>`**: hash `{epoch, level, at}`, `EX 604800` (7 days); its existence = that request id has been published. `PUBLISH_LUA` writes it last, after every other write; when the same `id` is published again, `PUBLISH_LUA` sees it and returns `{'dup', epoch}` with zero writes. The same request replayed after more than 7 days is treated as a new request (the epoch goes up once more, the safe direction).
  - **Z4 `fx:channel:stop_done:<epoch>`**: hash, `EX 604800`. Fields: for each handled worker slot `<slot>`, the value goes `attempted:<ts>` (claimed with `HSETNX` before the key press) → `sent:<ts>` (`send_key` returned true) or `send_failed:<ts>` (returned false or raised); `done` (when this epoch finished processing); `audited` (the `security.stop stage=daemon` audit has been written). Read and written only by the daemon-side `stop.daemon_tick`. A slot interrupted after the claim and before the result is recorded stays `attempted:*` and is reported as `unknown` in the audit (not counted as pressed). At most one Escape per slot per stop request; a durable request does not guarantee that every slot was pressed; `sent` only means the backend accepted the key press.
  - **Z5 `PUBLISH_LUA`: validate before writing, no rollback promised**: publishing `/stop` is a Lua script with a `#!lua` shebang that does not declare `allow-oom` (`KEYS = [fx:service, fx:channel:stop, fx:channel:stop_req:<id>]`, `ARGV = [id, level, rank, at, by, reason]`), shared by the actor's `/stop` and the daemon's import of stop flags. **Validate first, then write**: `id` is 32 hex chars; `level ∈ {pause, interrupt, kill}` and `rank` matches it; `at` is a finite positive number; `by` ≤ 64, `reason` ≤ 400; `TYPE fx:service ∈ {hash, none}` and `stop_epoch` has the Z1 shape; `TYPE fx:channel:stop ∈ {hash, none}` and its `rank ∈ 1..3`, its `epoch` has the Z1 shape; `TYPE stop_req:<id> ∈ {hash, none}` (already present with a well-formed `epoch` → return `{'dup', epoch}`). Any failure → return `{'invalid', <item name>}` with **zero writes**. After validation the write order is fixed: ① `HINCRBY fx:service stop_epoch 1`; ② `HSET fx:service paused 1 reason <reason> at <at>` (`at` must differ from the old value, otherwise add 1 µs — this makes the handoff auto-resume give up); ③ merge `fx:channel:stop` (Z2); ④ write `stop_req:<id>` and `EXPIRE 604800`; ⑤ return `{'ok', epoch}`. **A Redis Lua error does not roll back writes already executed; this protocol does not promise all-or-nothing**: validation before writing rules out the known command errors; the dedupe record is written last, and any half-write (an unforeseen command error, a process crash mid-run) is completed by replaying the same `id`, at the cost of the request's epoch going up at most once more (only upward, the safe direction). **Behaviour under out-of-memory (OOM) is not guaranteed**: "rejected for lack of memory before the script starts, with zero writes" relies only on the shebang semantics and has not been tested; implementation, docs and receipts must not claim it.
  - **Z6 `RELEASE_LUA`**: after the daemon finishes an epoch `E` (`stop_done:<E>` has `done` and `audited`) it runs: `if TYPE fx:channel:stop == 'hash' and HGET fx:channel:stop epoch == E then DEL fx:channel:stop end`. If a new `/stop` advanced `epoch` during processing, the key is not deleted and the next tick handles the new epoch; a stronger level is never lost thanks to Z2's merge.
  - **Z7 stop flag: claim / read / acknowledge consumption**: stop flags live only in this run's directory, under `<run>/state/` (0700): `stop.flag` (0600, JSON `{"requests": [req, …]}`, `req` fields as Z2's `id / level / by / at / reason`), `stop.flag.lock` (writer lock), `stop.flag.tmp-<uuid>`, `stop.flag.claim-<uuid>`, `stop.flag.bad-<ts>`; `config_dir()/state/` is not used, and other runs are never read. **Writer (actor)**: hold `fcntl.flock(stop.flag.lock, LOCK_EX)` (cross-process mutual exclusion) → read the existing `stop.flag` (bad JSON → first rename it `.bad-<ts>`) → append → write a temp file → `os.replace` it onto `stop.flag` → unlock; if the replace fails the original file is unchanged. **Consumer (daemon)**: first replay any leftover `stop.flag.claim-*`; then **claim** with `rename(stop.flag → stop.flag.claim-<uuid>)` (never reads the original name, never unlinks the original name); read the claim file and call `PUBLISH_LUA` for each `req` (`ok` / `dup` count as success; `invalid` → audit and rename the claim file `.bad-<ts>`); **the claim file is `unlink`ed only after every request in it has been published successfully (acknowledged consumption)**. Any failing step or crash → the claim file stays and the next tick replays it (deduped by id: no extra epoch increments, no repeated key presses).
